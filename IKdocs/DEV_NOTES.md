# IKBT Developer Notes

Rationale, measurements, and rejected alternatives that used to live in source comments.

The source files say **what the code does**. This file says **why it ended up that way** —
dated decisions, numbers someone measured once, and designs that were tried and abandoned.
Nothing here is needed to read or modify IKBT; it is here so the source can stay short.

For what to run and what each test asserts, see [TESTING.md](TESTING.md).
For release history, see [oldNews.md](oldNews.md).

## ikSolver.py

**`PERFORMANCE_OUTPUT`.** Measured across the robot set, 37–85% of a solve's wall clock is
inside `sp.simplify()`. The sympy meter prints a line per slow call, which is the only output
that can appear *during* a blocking simplify — `symbolic_loop`'s per-pass line cannot print
until the pass returns. Left off by default because in an ordinary run it buries the per-pass
progress lines it sits between.

**Per-robot debug blocks.** ikSolver.py used to end with roughly 200 lines of commented-out
per-robot debug setup. `build_default_bt()` now returns a `nodes` dict, so any node's `BHdebug`
can be set by name from a caller; the commented blocks were deleted.

**Solution-set finding is at version 3.** Version 2 was tree-based and went through
`R.notation_collections` / `matching.matching_func()`. That path is gone;
`create_solution_set()` replaced it, called exactly once by the `output_gen_full` leaf.

## ikbtfunctions/ik_driver.py

**Why the pipeline is a module of functions.** It used to run at module level inside
ikSolver.py, so importing any part of it triggered a full solve and a second front end
would have had to copy all of it.

**Why equation width is measured, not predicted** (`write_latex_fitted`). Two cheap proxies
were tried and both failed on real data:

- *Character count.* A 439-character equation overflows the page while a 2030-character one fits.
- *Operation count.* Brad's `th_3` is 25 operations with 12 in each `atan2` argument — under every
  threshold tried — and its typeset line is 144 pt too wide.

Width is a property of the typeset line, not of the expression, so `pdflatex` is asked. `Craig417`
needed three shortening passes: shortening one equation exposes another.

`slack_pt = 6.0` exists because Stanford has one box 3.7 pt over, about one character wide.
Restructuring a readable equation to win that back trades it for a folded one.

**Reporting must never cost the report.** The width loop degrades to pass 1 on any failure —
missing `pdflatex`, LaTeX error, timeout — because the pass 1 report is already written and
already correct, merely wide.

## ikbtleaves/symbolic_loop.py

**Why this leaf owns its own loop** instead of using `b3.RepeatUntilSuccess(solveRoutine, 10)`.
`RepeatUntilSuccess` returns FAILURE when it exhausts its loops, and a FAILURE at the top of a
Sequence aborts the Sequence — so once anything sits downstream of the solver (codegen, or the
hybrid branch), a loop-exhausted *partial* solve would be discarded even though IKBT has always
reported partial solves. Wrapping the decorator in `Priority([..., Succeeder()])` hides the
real failure too, leaving the tree unable to tell "solved nothing" from "ran out of passes".
Owning the loop in ordinary Python lets `tick()` choose its exit status and answer the one
question the rest of the tree needs: did the symbolic solver get anywhere?

**`require_complete = True`** (BH, 2026-08-23). A closed form for 1 of 7 joints is not inverse
kinematics, so the node must not report SUCCESS for it and let a report be written. It was
`False` — SUCCESS whenever *any* variable was solved — which was indistinguishable from `True`
until Issue4's derived arm came in at 1 of 7, the first partial solve in the robot set.

Nothing is discarded by this: `set_solved()` has already mutated the solved unknowns, so the
partial result is still on the blackboard and available to any caller. Only the tree's verdict
changes. *Future work:* use a partial result deliberately — solve what is left numerically in
the lower-dimensional space the solved variables leave behind.

**`progress = True`.** This node is the only place that knows both the pass number and the
budget, so it is the only place that can print "pass 4 of 10" — the answer to "is this stuck or
just slow". Set it False in tests that assert on captured output.

## ikbtbasics/numeric_ik.py

**Measured on Puma**, seeded by perturbing a pose generated by its own FK:

| perturbation | converged | mean iterations |
|---|---|---|
| 0.05 rad | 10/10 | 3.0 |
| 0.20 rad | 10/10 | 4.0 |
| 0.50 rad | 10/10 | 5.6 |
| 1.00 rad | 10/10 | 10.2 |
| 2.00 rad | 10/10 | 19.2 |

The error sequence is quadratic — `1.9e-01  1.6e-02  3.4e-04  1.0e-07  2.3e-15` — which is
what says the step is a real Gauss-Newton step and not merely a descent direction.

At the Puma **wrist singularity** (`th_5 = 0`, joints 4 and 6 colinear) it still converged
10/10. An undamped Newton step is singular there by construction, so this is the damping
earning its place; plain gradient descent would have made that failure mode permanent.

**Why damped least squares and not plain gradient descent.** `dq = J'(JJ' + lam^2 I)^-1 e`
behaves like Newton away from singularities and degrades *gracefully* to gradient descent as
`lam` grows. That graceful degradation is the whole point at a 6R wrist singularity.

**Two properties checked once, relied on since.**

1. `T_06` (4×4) and `J66` (6×6) are already pickled for all 32 robots, and their free symbols
   are exactly the joint variables plus the params in `pvals`. No new symbolic computation.
2. Sum-of-angle symbols cannot appear in `T_06` or `J66`. This is structural, not statistical
   (BH): every link carries exactly one joint variable, so a DH link transform has nothing for
   a `th_23` to be. SOA terms arise *within* the FK equations as the SOA scan rewrites them,
   and that rewriting lands in `matrix_equation.Ts`, not in the product `T_06` or in `J66`.
   So there is nothing to re-check when robot 33 arrives. (BH notes an SOA simplification
   *candidate* could in principle appear in a Jacobian term; finding it would be of minimal
   benefit, so nothing looks for one.)

**`pvals` used not to be uniformly numeric.** Craig417 and Raven-II are the only robots whose
alpha is not a multiple of π/2, so they are the only ones for which `forward_kinematics()`
invents `ca_i`/`sa_i` at all. It used to write the *strings* `'np.cos(al_1)'` /
`'np.sin(pi/4)'` into `pvals`, and those symbols really are in `T_06`, so they had to be
resolved rather than skipped — `dh_analysis.numeric_pvals()` *drops* them, which is right for
its own zero-tests and wrong here, because a dropped `ca1` survives as a free symbol and
becomes a spurious lambdify argument. Since 2026-09-03 `forward_kinematics()` evaluates them,
so every pval on every robot is a number; `pvals_numeric()` remains as the guard and
`_lambdify_checked()` refuses anything left over.

**Cold-cache cost.** `TestSolver022` runs in ~1.5 s with warm FK pickles. Its first ever run
took minutes, because it was the first thing in the suite to load Craig417 and Raven-II and
their FK had to be computed and cached.

## ikbtbasics/kin_cl.py

**Why `set_solved()` has a re-entry guard.** Without it, a second solve gave the variable a
duplicate column in the version matrix and inflated the solution count: ICP5p5_A21 solved
`th_1` twice and reported 12 versions where 3 is right; Parkman13 the same.

Returning early was not enough. A solver leaf appends to `self.solutions` and overwrites
`self.nsolutions` *before* it calls `set_solved` (`tan_solver.py` is the one that reaches
here), so by the time the guard sees the call the damage is done — `solutions` ends up longer
than `solutionNames`, and every consumer that walks `solutions` while indexing
`solutionNames[i]` runs off the end. Measured on Parkman13: `th_1` solved with 2 solutions, a
later pass proposed a third by `atan2`, and `output_latex_solution` died with `IndexError`.
Nothing caught it until 2026-09-05 because the batch runner had codegen off, so `report_gen`
never ticked.

**Version names vs. solution names.** `versionNames` used to append
`solutionNames[i % nsolutions]`, so it was just the solution names repeated — `th_3` with 4
versions reported `['th_3s1','th_3s2','th_3s1','th_3s2']`. `create_solution_set()` seeded the
first solved unknown's column from that list, putting *solution* names in column 0 of
`solListMatrix` while every other column held *version* names, and everything downstream then
referenced a `th_1s1` that is never assigned anywhere.

**Why `pvals` stores numbers, not strings** (BH, 2026-09-03). `forward_kinematics()` used to
write `'np.cos(al_1)'` into `pvals`. `numeric_ik` then had to special-case the strings, and
`output_python` emitted `ca1 = np.cos(al_1)` into generated code, which worked only as long as
`al_1` happened to be in scope there.

## ikbtbasics/eqn_sanity.py

**The UR5 tautology** (measured 2026-08-28) is why this module exists. The equation IKBT used
to solve `th_2` was

    0 = A*sin(th_2) + B*cos(th_2)

    A = -r_31*s5*c6 + r_32*s5*s6 - r_33*c5
    B = -(r_11*c1 + r_21*s1)*s5*c6 + (r_12*c1 + r_22*s1)*s5*s6
        - (r_13*c1 + r_23*s1)*c5

Substituting UR5's own symbolic `T_06` gives `A == 0` and `B == 0` *identically* — proved with
`a_2, a_3, d_1, d_4, d_5, d_6` left as free symbols, so it holds for every parameter value and
every pose. `th_2` does not appear in the coefficients at all; the equation reduces to
`0*sin(th_2) + 0*cos(th_2) = 0`, satisfied by every value of `th_2`.

`sinANDcos` then evaluated `atan2(-B, A) = atan2(0, 0)` and reported an answer. Across the 8
solution versions `th_2` came back as 0.000, 3.142, 2.614, 5.773 … against a true −0.600, and
**not one** of the 8 versions reproduced the pose. The robot was recorded as "solved 9/9"
throughout, because nothing checked.

## ikbtbasics/dh_analysis.py

The collinear case (trap 2 in the module header) is not a corner case: Stanford, Bartell,
Palm13, Srisuan11 and Raven-II all have two of three consecutive axes on the same line, so
their triples are concurrent for *any* `d_n1`, including a prismatic joint variable.

`scripts/axis_triple_check.py` exists because all three traps fail silently. It checks every
rule in the module header against numeric FK geometry across the whole robot set.
